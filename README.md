# Notify

A small real-time notification system: an Encore.ts backend backed by PostgreSQL, and a Bun TypeScript CLI that talks to it over HTTP.

- `notify-backend/` Encore.ts API with two services, `users` and `notifications`.
- `notify-cli/` Bun CLI, compiled to a single executable.

## Prerequisites

- [Encore CLI](https://encore.dev/docs/install)
- [Bun](https://bun.sh)
- Docker (Encore runs local PostgreSQL in a container)

## Backend

```sh
cd notify-backend
encore run
```

- API: http://localhost:4000
- Local dashboard (API explorer and request traces): http://localhost:9400

Encore provisions PostgreSQL and applies migrations automatically on start.

Run the tests (isolated test databases, no mocking of infrastructure):

```sh
cd notify-backend
encore test
```

### Endpoints

| Method | Path | Description |
| --- | --- | --- |
| POST | `/users` | Create a user |
| GET | `/users` | List users |
| POST | `/notifications` | Create and send a notification |
| GET | `/notifications?userId=<id>` | List a user's notifications |
| GET | `/notifications/unread?userId=<id>` | List a user's unread notifications |
| POST | `/notifications/:id/read` | Mark a notification read |

Channels are `in_app` and `email`. The email channel is simulated: a structured log line plus the stored record.

## CLI

Build the single binary:

```sh
cd notify-cli
bun install
bun run build        # bun build --compile ./src/cli.ts --outfile notify
```

This produces `./notify`. The backend URL is resolved in this order: `--api-url`, then `NOTIFY_API_URL`, then `http://localhost:4000`.

```sh
./notify users:create --name="Ahmed" --email="ahmed@example.com"
./notify users:list

./notify send --user-id=<user-id> --channel=in_app --title="Hello" --body="Welcome!"
./notify list   --user-id=<user-id>
./notify unread --user-id=<user-id>
./notify read   --id=<notification-id>

./notify --version
NOTIFY_API_URL=http://localhost:4000 ./notify users:list
```

Output is pretty-printed JSON. The CLI only talks to the backend over HTTP and never touches the database.

## Architecture and choices

- **Two Encore services, one database each.** `users` and `notifications` are independent, which keeps ownership clear and uses Encore's service model.
- **No cross-service foreign key.** A notification's `userId` cannot be a database foreign key because `users` lives in a separate service database. `send` instead validates the recipient with a typed service-to-service call to an internal `users.get` endpoint.
- **Validation via Encore's type system.** Rules like `IsEmail` and `MinLen<1>` are expressed as types, so invalid input is rejected with a 400 before handler code runs.
- **UUID primary keys** generated by Postgres (`gen_random_uuid()`).
- **Read state as a timestamp.** `read_at` is nullable and `read` is derived. `markRead` is idempotent: `COALESCE(read_at, now())` keeps the first read time.
- **CLI.** Commander for predictable parsing, a thin `fetch` client, and pretty JSON output so the API response stays the single source of truth. Bun compiles it to one self-contained binary.
- **Tests.** Vitest run through `encore test`, which provisions real isolated databases per run rather than mocking infrastructure.
